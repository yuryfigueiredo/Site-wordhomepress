# Automação — as três camadas

Node puro: sem npm, sem dependência, sem serviço pago. As chaves de API usadas são a do Gemini/NVIDIA (free tiers, só pela Camada 3) e a do Unsplash (`UNSPLASH_ACCESS_KEY`, para achar foto real). Rodam na sua máquina com o Node que já existe (v24). Desde 13/11 a Camada 3 também roda **aqui** — é o timer `hwp-turno` quem dispara e empurra a rodada; o `.github/workflows/turno.yml` continua no repo como a agenda que o doctor confere, mas está **desabilitado** na aba Actions.

```bash
node tools/doctor.js            # varredura completa (inclui links externos)
node tools/doctor.js --offline  # sem rede: assets, metadata, catálogo, sitemap
node tools/doctor.js --quick    # só catálogo + assets + metadata
node tools/ingest.js            # atualiza a fila de pautas
node tools/ingest.js --show     # imprime a fila de hoje
node tools/build-sitemap.js     # regenera sitemap.xml a partir do catálogo
node tools/build-dist.js        # monta dist/ para upload (ver PUBLISHING.md)
```

## `doctor.js` — o que ele pega sozinho

| Checagem | Erro quando |
|---|---|
| `asset-missing` | arquivo referenciado em HTML/DB não existe no disco |
| `asset-not-image` | `.jpg`/`.png` que na verdade é HTML salvo (foi assim que o `toyman_cover.jpg` quebrou) |
| `internal-link` / `anchor` | link interno não resolve, âncora sem alvo |
| `date-rot` | data relativa tipo "2 HOURS AGO" no catálogo |
| `meta-*` | página sem title/description/canonical/og:image/favicon; 404 sem `noindex` |
| `a11y-input` | `<input>` sem label |
| `sitemap-drift` | artigo publicado ausente do sitemap |
| `feed-stale` | o `feed.xml` commitado não é exatamente o que `build-feed.js → buildItems()` escolhe hoje (matéria nova fora do RSS — foi assim que o feed ficou parado no Hubble por cinco publicações com o robô verde) |
| `cadence-override` | publicação dos últimos 7 dias marcada `forcada:true` em `pipeline/memory.json` (aviso: alguém furou o teto com `--force-cadence`, e agora isso é contável) |
| `repetition` | dois artigos publicados abrindo com as mesmas palavras, ou com o mesmo padrão rítmico |
| `orphan` | matéria ou review que nenhuma OUTRA página tem link para ela (a própria página é o destino, não a entrada) |
| `affiliate` | link Amazon/Audible sem `tag=`, ou tags inconsistentes entre si |
| `cover` | `cover_changes_per_day` ≠ número de horários do `check_hours`, `cron_expression` ≠ workflow, nenhuma matéria acima do piso da capa, ou acervo sem para onde girar |
| `picks` | `picks_changes_per_day` ≠ 1, slot sem `"rotacao": "dia"`, pool abaixo do mínimo para trocar todo dia, o par publicado ≠ o par que a régua de hoje calcula, card `pick-item` fora dos marcadores, picks repetindo a capa ou sem artigo no catálogo |
| `placeholder-copy` | texto de rascunho visível ao público (ex.: o bloco "ADVERTISEMENT // …") |
| `external-broken` | link externo devolvendo 404/500 |
| `external-blocked` | 401/403/406/429 — provável bloqueio a robô, abre manualmente (aviso, não erro) |

Saída: console + `tools/reports/AAAA-MM-DD.md`. Código de saída `1` quando há erro — é isso que o agendador usa para saber que algo mudou.

## `ingest.js` — de onde vêm as pautas

12 feeds públicos gratuitos (Publishers Weekly, Reactor, Guardian SF, Publishing Perspectives, SFWA, Ars Technica, The Verge, Hacker News, Science Daily, Phys.org, Space.com). Nenhum exige cadastro.

Cada item é pontado pelos vocabulários dos 5 pilares, descartado se parecer tema já publicado, deduplicado por título e limitado a 8 pautas por fonte. O resultado vai para:

- `pipeline/leads/AAAA-MM-DD.json` — estrutura para consumo por script
- `pipeline/leads/AAAA-MM-DD.md` — a mesma fila legível, com pilar, registro sugerido e url
- `pipeline/state/seen.json` — URLs já vistas (últimas 4000). **Só vale na sua máquina**: `state/` é gitignored (com duas exceções versionadas, abaixo), então num runner limpo ele nasce vazio todo turno. O que impede a fila de repetir o que já está no ar, em qualquer lugar, é `pipeline/memory.json` + as fontes do catálogo (ver Camada 3).
- `pipeline/state/cover-state.json` e `pipeline/state/hero-fallback.html` — **versão no git**, porque a memória da capa tem de sobreviver a um runner limpo: sem `cover-state.json` cada rodada acordaria acreditando que nunca trocou a capa, e sem o fallback a capa escrita à mão sumiria do `index.html` no primeiro build.

Cada pauta traz `pillar`, `register` e `fit`. Isso é o insumo da Camada 2: quando você quiser escrever, a pauta já vem com o encaixe editorial decidido — mas a decisão de escrever continua sua.

O que o `ingest.js` **não** faz: não acessa a Amazon, não verifica preço, não confirma fato, não escreve.

## Agendar nesta máquina (uma vez, sem instalar nada)

Desde 13/11 o relógio do site **é** esta máquina: `~/.config/systemd/user/hwp-turno.timer` dispara `~/.local/bin/hwp-turno.sh`, que espelha os passos do workflow e termina em `node tools/turno.js` + commit `turno:` + push. O workflow do Actions está desabilitado, e o script se recusa a começar sem a prova local de que ele foi desligado (`~/.local/state/hwp/actions-desligado`) — dois relógios no mesmo minuto escreveriam em `pipeline/memory.json` ao mesmo tempo.

As duas unidades estão fora do repositório de propósito: a proibição do AGENTS.md é *nenhum script de `tools/` chama push*, e quem empurra é o operador, não o repo. Conferir e mexer:

```bash
systemctl --user list-timers 'hwp-*'      # próxima elapse do turno e do vigia
systemctl --user start hwp-turno.service  # rodada agora, pelo caminho inteiro
journalctl --user -u hwp-turno.service -n 50   # o que a última rodada disse
tail -20 ~/.local/state/hwp/avisos.log    # o que os portões avisaram (verde e vermelho)
touch ~/.local/state/hwp/actions-desligado     # só depois de desabilitar na aba Actions
```

O log é `~/.local/state/hwp/turno.log` (`StandardOutput=append:` do serviço), porque o `TURNO.md` commitado é a versão pública da mesma sequência. Diferenças que importam contra o runner da nuvem: o script **recusa árvore suja** antes de tocar em qualquer arquivo (o recuo geral da rodada vermelha é `git checkout HEAD -- .`, e num clone descartável isso é seguro; na sua máquina apagaria trabalho seu), e `Linger=yes` + `Persistent=true` existem para a rodada perder o horário e ainda assim ser feita no boot seguinte, em vez de sumir do dia — que era o defeito medido do scheduler do Actions.

### Quem avisa, e quem confere se o aviso era preciso

Ninguém abre `turno.log` todos os dias, e um relógio que é um portátil falha calado: tampa fechada, bateria no fim, rede fora do ar. Duas unidades a mais moram fora do repo por isso:

- **`~/.local/bin/hwp-aviso.sh <origem> <mensagem>`** é a boca única. Escreve em `~/.local/state/hwp/avisos.log` **sempre** — é o registro que sobrevive — e tenta `notify-send` na área de trabalho, cujo fracasso é silencioso por desenho (sem sessão gráfica não há notificação, mas a linha fica). O `hwp-turno.sh` chama o aviso em toda saída vermelha (árvore suja, sem rede, dois relógios, redator desarmado, commit ou push que não passaram) e, na verde, quando o contador de publicações do dia subiu — a conta é `lib/cadence.publishedToday()`, a mesma função que o teto lê, não um palpite sobre o `TURNO.md`.
- **`hwp-vigia.timer`** (uma olhada por hora, às :41 — nunca no minuto da rodada) roda `~/.local/bin/hwp-vigia.sh`, que lê a régua de `pipeline/cadence.json` e pergunta o que o doctor não pergunta: **a rodada do horário aconteceu?** A resposta vem de um cabeçalho `===== turno local …` no `turno.log`, com 90 min de folga (o `AccuracySec`, as 3 tentativas de rede e os 45 min de timeout do turno). O cabeçalho é escrito no **começo** da rodada, então ele prova que a rodada abriu, não que serviu: o vigia lê o bloco entre aquele cabeçalho e o próximo e, se houver `VERMELHO` ali, o aviso é **"rodada vermelha"**, com a causa que o runner escreveu. Medido em 13/11: às 20:23 a rodada abriu, morreu no portão da árvore e o vigia cantou "servida e empurrada" — a mesma família do teto cego e da capa parada. Depois pergunta se ela chegou ao ar: `origin/main..HEAD` com commit local à frente é a peça escrita que o site não vê. E confere o fuso: o `OnCalendar` corre no fuso **do sistema**, enquanto `check_hours` declara um fuso — divergindo, os horários do timer não são os da régua, e o doctor continua verde porque ele compara o JSON com o cron do arquivo.
- Uma rodada perdida ou vermelha é avisada **uma vez** (`~/.local/state/hwp/vigia-ultimo` guarda o slot já cobrado), para o vigia não virar spam de hora em hora. Cada aviso leva a própria etiqueta no `avisos.log` — `rodada perdida`, `rodada vermelha`, `push pendente`, `fuso` — porque as quatro são defeitos diferentes com a mesma caixa de notificação.
- O portão da árvore do runner perdoa **um** arquivo: `TURNO.md` sozinho é o diário que o próprio runner commita em toda rodada, e uma rodada à mão (`node tools/turno.js`, o caminho manual do AGENTS.md) deixa exatamente ele sujo. Com mais qualquer caminho na árvore, a rodada para como sempre parou — perdoar o diário não é apagar trabalho do dono.

Prova do vigia: `node .audit/teste-vigia-local.js` (28 conferências — servida e empurrada muda, rodada perdida avisa uma vez e não avisa de novo, rodada vermelha avisada com a causa sem cantar verde, o vermelho de um horário antigo não mancha o verde do seguinte, push pendente contado, fuso divergente, slot dentro da folga calado, e nada do teste escreve no estado real da máquina). Prova do portão da árvore: `node .audit/teste-runner-portao.js` (18 conferências — o runner real roda contra um fixture no /tmp pelas bocas `HWP_REPO`/`HWP_STATE`/`HWP_AVISO` e para em `HWP_SO_PORTAO`, que é a única parte dele conferível sem queimar uma rodada no repo de verdade).

`pipeline/drafts/`, `pipeline/leads/`, `pipeline/state/seen.json` e `tools/reports/` são gitignored mas **persistem aqui**, o que não acontece no runner: lá cada rodada acordava com a fila de vistos vazia. A régua de repetição continua sendo `pipeline/memory.json` + as fontes do catálogo, que são versionadas e valem em qualquer lugar.

## Publicação de posts (Camada 2)

Quatro comandos. O passo de escrever o texto pode ser seu (colar `prompt.md` no chat) ou do robô agendado (Camada 3):

```bash
node tools/ingest.js                 # fila de pautas (camada 1)
node tools/new-post.js 3             # pauta nº 3 → pipeline/drafts/<slug>/{brief.json,prompt.md}
#   quem escreve: você, ou o turno agendado, seguindo prompt.md à risca
node tools/make-cover.js <slug>      # só para matéria SEM foto real: placa SVG → images/covers/<slug>.svg
node tools/check-post.js <slug>      # editor mecânico → review.md, exit 1 se reprovar
node tools/score.js --draft <slug>   # nota 0–10 calculada por rubrica (não é opinião)
node tools/publish.js <slug>         # só com check verde: catálogo + capa + feeds + sitemap + commit
```

- `pick-lead.js` só entrega pauta cuja fonte abre agora: feed de notícia às vezes publica item com link morto, e o editor mecânico reprova link 404 depois que o texto já custou chave. Pautas descartadas saem no stderr.
- `new-post.js` monta o brief no formato exato do input contract de `voice/WRITER_PROMPT.md`, escolhe a byline pelo território (`EDITORIAL_VOICE.md` §4) e embute a memória anti-repetição de `voice/state/last_runs.json` no prompt.
- `make-cover.js` desenha a miniatura sem banco de imagens e sem custo: placa 1200×675 em SVG, com a cor do pilar (a mesma de `css/styles.css`), o kicker e o título quebrado em até 4 linhas. É determinística — mesmo slug, mesma placa — e só preenche `image`/`imageAlt` quando o draft ainda está sem capa. O turno roda ela de novo depois de cada reescrita, porque o modelo devolve `image: null` e `write.js` preserva a capa anterior. **Matéria que já tem foto real (`images/posts/*.jpg`) sai dela com exit 0 e nenhuma placa gerada** — era exatamente esse `exit 1` que, desde 05/11, abortava todo `publish.js` de matéria com foto: o turno chamava a placa depois de a foto já estar no draft, a placa falhava, e o `publish.js` desfazia a publicação inteira.
- **Foto real é portão, não enfeite:** antes de inserir no catálogo, `publish.js` exige `image` (ou `bookCover`) apontando para `.jpg`/`.png`/`.webp` que não seja placa. Sem foto, chama `tools/find-cover.js` (busca em `tools/lib/find-photo.js`: Unsplash → Pexels), salva em `images/posts/<slug>.jpg` e grava crédito e autor no draft. Se nenhum candidato achar foto, a publicação **aborta** (exit 1, catálogo intacto) e `tools/notify-foto.js` abre uma issue no repositório com o log da busca — porque rodada abortada em silêncio foi exatamente como o site passou três semanas sem publicar.
- **De onde sai a foto (régua de 07/11):** a primeira query é o campo `photoQuery` do rascunho — 3 a 6 palavras em inglês nomeando a CENA que a foto deveria mostrar, escritas por quem escreve o texto. `check-post.js` reprova rascunho sem ele (gate `photo-query`), porque a query montada a partir da manchete já colocou no ar um render de "QUANTUM" numa matéria de íons presos: "two trapped ions let a gauge field" não é vocabulário de banco de imagem. O numeral e a palavra vazia são riscados da query por `palavrasConcretas()`, a mesma régua que o portão usa. E a foto deixada de fora do catálogo não é mais `results[0]`: pedem-se 5 candidatas e escolhe-se a cuja legenda (`alt_description`) aparecem palavras inteiras da query — prova de assunto que existe sem ver a imagem; empate se decide por curtidas. Se nenhuma das 5 legendas menciona a query, o candidato é recusado com motivo e a busca passa para a próxima query; esgotadas as queries, aborta como acima. `node .audit/teste-foto-query.js` (offline, fetch falso) e `node .audit/muta-foto-query.js` (desliga cada regra e exige teste vermelho) são a prova disso.
- `check-post.js` mede tudo no texto, não confia no `self_check`: tags permitidas, vocabulário banido (lista única em `WRITER_PROMPT.md`), templates estruturais (máx. 1, nenhum como fecho), ritmo (frase ≤30 palavras, frase curta obrigatória, 1 parágrafo de uma frase, 1 parágrafo longo), humor ≤2 e zero em pauta de morte, abertura/fecho diferentes da última peça do registro, fontes alcançáveis, links do texto presentes nas fontes, comprimento (abaixo de 70% do alvo da pauta é reprovado — o mesmo número que o prompt pede), e a regra dura: **"we tested" só com `products[].tested=true` e protocolo em `test_notes`**.
- `publish.js` insere no catálogo, roda `build.js` + `build-sitemap.js` + `build-feed.js` + `meta-pages.js` + `doctor.js`, atualiza `last_runs.json` e faz **commit local**. Se qualquer etapa falhar, restaura o catálogo e não publica. Nunca faz push, nunca faz deploy.

### Onde os cards novos aparecem

`tools/build.js` preenche, entre marcadores `<!-- hwp:auto:<slot>:start/end -->`, os feeds listados em `pipeline/placements.json`: o hero, o bloco TODAY'S PICKS, os subfeatures da coluna central, MOST RECENT e os grids de culture/tech/science na home, e o feed das três páginas de editoria. Nos feeds, a região automática só acrescenta no topo os ids que ainda não aparecem no resto da página. O desconto tem três modalidades por slot (`dedup`): arquivo inteiro (o padrão da home, onde os blocos dividem tela), `"prioridade-ineditas"` (páginas de categoria — o feed é o acervo e a ordem é régua: as matérias que a curadoria do topo já mostrou não podem abrir a lista, elas afundam para o fim; com desconto do arquivo o culture-feed ficava em 5 de 8 e o tech-feed em 1 de 8) e `"somente-automatico"` (grade CULTURE — só os blocos automáticos descontam; sem isso as duas matérias do TRENDING // TOP 5 tiravam vaga e a grade fechava com 5, abrindo um buraco de 437px na última linha de uma grade de 3 colunas). Os feeds de editoria trazem ainda `"acervo": true`, que corta o cap: com `limit: 8`, a página de science listava 11 das 15 peças e a de culture 8 das 10 — e as cortadas não eram as mais velhas, eram as que o `slice` alcançava. Duas matérias do catálogo (uma de cada editoria) não tinham nenhum link de entrada em lugar nenhum do site (medido no HEAD em 09/11). A exceção declarada é o bloco de picks (`"rotacao": "dia"`): ali o desconto é só a região do hero, porque picks é bloco de descoberta e a matéria pode, sim, estar também no feed de cultura logo abaixo.

O build tem dois modos. O completo (sem flag) refaz todos os slots, sincroniza os contadores `count_pill` e gira a capa — é o que o `publish.js` chama e o que o `turno.js` chama no fim de uma rodada que não publicou. O `--daily` processa **só** os slots com `"rotacao": "dia"`, pula os contadores e não toca no hero nem em `pipeline/state/cover-state.json`: é o passo 2 da rodada, antes da manutenção, porque o doctor exige o bloco de hoje no ar e o build completo gastaria a única troca de capa da rodada antes de a matéria inédita tomar o hero. `--dry` continua valendo nos dois (mostra sem gravar). Prova de que o `--daily` não encosta na capa: `node .audit/teste-trava-picks.js` — 22 conferências com relógio falsificado, conferindo o hash do `cover-state.json`, o HTML do hero e o resto do `index.html` antes e depois, mais a idempotência de rodar duas vezes. A ordem no `turno.js` é provada no mesmo arquivo e mordida por duas mutações (passo 2 apagado, ordem invertida com a manutenção): sem isso, tirar a correção do turno deixaria a bateria verde, porque o teste do mecanismo nunca executava o turno.

As cinco escritas versionadas do pipeline (`build.js` no HTML e no fallback da capa, `lib/lastRuns.js`, `lib/memory.js` e `lib/cover-state.js` na memória da capa) passam pelo `tools/lib/atomic-write.js`: `tmp + rename`, com o rename repetido até 6 vezes (600 ms de fôlego no pior caso) **apenas** quando o erro é trava de arquivo — `EPERM`, `EACCES`, `EBUSY`. Motivo medido em 10/11: no Windows o antivírus/indexador segura o alvo por um instante depois de o `tmp` ser escrito, e o `renameSync` estourava com `EPERM ... rename 'index.html.tmp' -> 'index.html'`, derrubando a rodada sem pauta ruim, sem nota baixa e sem régua furada. Erro de outra natureza sobe na primeira tentativa: `ENOENT` de caminho errado não ganha seis chances para continuar errado. O `cover-state.json` e o `hero-fallback.html` entraram na mesma passada porque eram escrita direta: um kill no meio truncava o JSON, e o `loadState` engole truncamento devolvendo estado vazio — a memória da capa zerada em silêncio, sem erro nenhum no log. Prova: `node .audit/teste-trava-arquivo.js` (o helper, os gravadores de registro, a memória da capa, o build inteiro com a trava simulada por preload, a mutação que devolve o `fs.renameSync` cru e vê o build morrer com uma falha só, e a invariante de que nenhum `renameSync` cru sobrou em `tools/`).

**Nada na home é escrito à mão, salvo as exceções declaradas** (09/11). Sobravam 28 cards fora dos marcadores entre `index.html` e as três páginas de editoria: eles nunca eram regenerados (a grade CULTURE mostrou as mesmas 6 peças por semanas sob um rótulo que promete novidade) e entravam na conta de ids já usados, congelando o próprio slot — CULTURE tinha `limit` 6 e gerava 3. O mesmo mecanismo deixou a coluna central da grade de 3 colunas com um vão preto de 807px ao lado do hero. O portão `[slot-stale]` do `doctor.js` (via `tools/lib/slot-markup.js`, o módulo que diz o que é card de slot e onde fica a região) quebra vermelho se um card de matéria do catálogo voltar para fora dos marcadores, e também se o rótulo `count_pill` (ALL CULTURE) discordar da grade. Ficam à mão o que o portão não enxerga porque a CLASSE do card não é classe de slot: a lista TRENDING // TOP 5, os `rec-card` de reviews, as duas placas do Dumarest (`dumarest/index.htm`), os 3 cards de spotlight no topo de cada página de editoria e os blocos de `reviews.html` (arquivo sem marcador nenhum). Nem tudo aí é curadoria fora do catálogo — os spotlights e os cards de `reviews.html` apontam para peças do catálogo e também não são regenerados por ninguém; a diferença é que não roubam vaga de slot, então o defeito que eles produzem é data apodrecendo, não grade congelada. Trazer esses blocos para o build é decisão do dono. Prova: `node .audit/muta-slot-stale.js` (11 casos — matéria solta na home e na editoria, classe com variante `is-featured`, review escrita à mão, pill discordando da grade, ordem do feed, falta de acervo, os três de alcance (a última entrada linkada apagada, a mesma falta com o slug citado num `<script>` em vez de linkado e uma review nova que nenhuma página linka) e a curadoria sem link de catálogo que o portão não pode morder — cada um restaurando o arquivo byte a byte; os de alcance plantam o defeito em duas páginas ao mesmo tempo).

A capa (`index-hero`, modo `replace`) é a exceção: ela é **substituída por uma matéria do pipeline que passe o piso** `cover_baseline` em `pipeline/cadence.json` (hoje 6.5) — qual delas é a régua de rotação abaixo. A nota é peneira de qualidade, não troféu: as notas não decaem depois de publicadas — a atualidade é medida no dia em que `score.js` avalia —, então escolher por "maior nota de todos os tempos" deixaria a mesma matéria na capa por semanas. Só competem matérias com nota medida por rubrica (`auto`) ou ajustada por você (`manual`): o acervo antigo (`baseline`) fica de fora porque o HTML escrito à mão dele carrega dek, alt e botão que o catálogo não tem. Quando nenhuma passa do piso, o HTML da capa escrita à mão — guardado em `pipeline/state/hero-fallback.html` — volta ao lugar, e é ressincronizado quando você edita a capa à mão. A imagem do hero usa a variante `-hero.svg` da placa (sem título gravado, porque o H1 vem logo abaixo); `tools/make-cover.js` escreve as duas de uma vez e `--from-db <id>` regera ambas a partir do catálogo, que é a fonte da verdade do título. **Foto real vai ao hero sem variante** — `heroImg()` só troca por `-hero.svg` quando a imagem é uma placa `images/covers/*.svg`.

A régua de **rotação** é por rodada: `cover_changes_per_day` (hoje 4) tem de ser igual ao número de horários do `check_hours`, porque **a capa gira em toda rodada do turno**, com matéria nova ou não — a capa é o que mais chama atenção e o hero não pode ficar parado horas a fio entre uma rodada e outra (com 4 horários são 4h de intervalo, contra as 8h da régua de 2 rodadas). A unidade foi a janela (dia 03:00–12:59 / noite 13:00–02:59, 2 trocas/dia) até 2026-11-07; com seis rodadas por dia, a janela conteria três rodadas e a meta cobraria duas. A régua é o log `changes` de `pipeline/state/cover-state.json`, e **só o `build.js` o escreve**: `publish.js` carimbava a rodada como "servida" mesmo quando a matéria publicada não passava do piso e continuava não sendo capa.

A escolha, em ordem (`pickCover`): **matéria que ainda não passou pelo hero** toma a capa na primeira publicação da rodada (é o caminho de toda publicação nova), e sem inédita acima do piso a rodada **caminha um passo na lista de elegíveis** (`proximaNaRotação`), voltando ao topo no fim do ciclo. Medido em 07/11 com três publicações na mesma rodada: a primeira virou capa, a segunda e a terceira saíram `capa mantida` — a trava da rodada vem antes da inédita, então quem publica depois da primeira troca espera a rodada seguinte. É por isso que a novidade é medida por ID (o conjunto `capaVistas`), não por data: `a.date` do catálogo tem granularidade de dia, então "a mais nova do catálogo" não distingue a matéria publicada agora da que a rotação acabou de derrubar — e foi assim que o segundo build da mesma rodada desfazia a rotação, registrando troca sem publicação enquanto o leitor via a capa em ping-pong.

Como o runner chama o build várias vezes por rodada, repetir a capa da rodada não conta como troca — e a trava é dupla: `registrarCapa` só grava se o HTML do hero mudou de verdade **e** se a matéria agora no ar é outra. Sem a segunda condição, um catálogo com uma única matéria elegível "girava" a capa para ela mesma em cada rodada nova e a meta subia sem nada ter mudado na página. Entradas com mais de 14 dias caem do log (`capaVistas` fica: é memória, não histórico). Quem confere a prova no fim é `tools/turno.js`: `capaServiuRodada()` lê o estado do disco e fecha a rodada em vermelho se não houve troca na rodada em curso — inclusive na que publicou, onde quem girou foi o build chamado pelo `publish.js`.

Três consequências disso ficam nos painéis de propósito:

- **Publicação e capa contam dias diferentes.** O teto de publicações é por **dia UTC** (é o dia do commit `publish:` no runner); a meta de capa é pelo **dia do fuso** do instante. Antes, com janelas, a rodada das 00:23 pertencia à noite do dia anterior e o painel mostrava 5/6 num dia que tinha cumprido as seis. Hoje as quatro rodadas (08:23, 12:23, 16:23 e 20:23) caem no mesmo dia do fuso. Às 21h de Brasília os dois dias já são outros — não é bug, é o relógio de cada régua.
- **A rodada que não publica também gira a capa.** `tools/turno.js` chama `build.js` ao encerrar qualquer rodada que passou pela manutenção sem publicar (teto, intervalo mínimo, falta de pauta): antes disso, a troca forçada só acontecia nos dias em que saía matéria, e a meta ia a zero em silêncio nos outros.
- **Rodada sem publicação não deixa foto no disco.** `turno.js` tira o retrato de `images/posts` e `images/covers` no começo e apaga o que nasceu durante a rodada em toda saída sem publicação — é o `garantirFoto()` dele que baixa o jpg, minutos antes de o `publish.js` existir como processo, então o retrato do publish não pegava nada. `publish.js` mantém o dele (mais o gancho de `process.on("exit")`, para exceção sem catch) porque alguém roda o publish à mão. `turno.js` tem o mesmo gancho: um throw sem catch derruba a rodada antes do `finish()`, e no runner a vermelho o recuo geral encobre isso — na máquina do dono, não: por isso o `hwp-turno.sh` recusa árvore suja antes de começar. Ctrl+C e o `timeout 45m` (aqui) / `timeout-minutes: 45` (no workflow) chegam por sinal, onde o gancho de `exit` não roda, então `SIGINT`/`SIGTERM` chamam o próprio `finish`, que desfaz as fotos, escreve o `TURNO.md` e sai vermelho.

Quem garante foto real antes de pedir a placa é `tools/turno.js`. O filtro "matéria que pode ser capa" (nota medida, foto, acima do piso) está em `tools/lib/cover-rules.js` e é o mesmo que `doctor.js` confere; as notas são injetadas no catálogo por `tools/lib/catalog-notes.js`.

## A nota (Camada 2.5): calculada, nunca digitada

`tools/score.js` dá 0–10 a cada matéria somando seis critérios, cinco deles medidos:

| critério | peso | o que mede |
|---|---|---|
| evidence | 2,5 | fontes únicas, domínio diverso, quantas são primárias e datadas |
| timeliness | 1,5 | idade da fonte mais recente |
| novelty | 2,0 | sobreposição de vocabulário com o catálogo (≥72% = quase-duplicata, −2,0 e bloqueio) |
| craft | 2,0 | o que `check-post.js` medeu em `metrics.json`: ritmo, léxico banido, humor, tamanho vs. brief |
| commercial | 1,0 | produto com preço, caixa de afiliado, protocolo de teste |
| judgment | 1,0 | o único ponto de opinião do modelo (`ranking.thesis_strength`, 0–2, com justificativa de até 25 palavras) |

Penalizações: `analysis_only` −0,5, quase-duplicata −2,0, sem imagem −0,5. O modelo **não pode declarar a nota** — se o draft trouxer `ranking.score`, o check reprova. Notas ficam em `pipeline/scores.json` (versionado), com origem `auto`, `baseline` ou `manual`. Nota manual só entra pelo painel com justificativa de 15+ caracteres, e o recálculo nunca a sobrescreve.

## Camada 3: o turno agendado (roda sem você)

O robô roda nesta máquina: `~/.config/systemd/user/hwp-turno.timer` chama `~/.local/bin/hwp-turno.sh`, que atualiza o `main` por fast-forward, roda `node tools/turno.js`, commita `turno:` e empurra. O `OnCalendar` é `*-*-* 08,12,16,20:23:00` no fuso do sistema = 11/15/19/23 UTC, os quatro horários do `check_hours` em `pipeline/cadence.json` e o mesmo cron escrito em `.github/workflows/turno.yml` — o arquivo continua no repo como a agenda conferível (é dele que `tools/lib/schedule.js` lê o relógio), mas o workflow está **desabilitado**: quem publica é o timer. A sequência, na ordem em que `turno.js` a executa: `ingest.js` → **`build.js --daily`** (gira só os blocos de `"rotacao": "dia"` — hoje o Today's Picks — sem tocar na capa nem no contador; vem antes da manutenção porque o doctor cobra o bloco de hoje no ar, e até 10/11 quem o produzia era o build do fim da rodada: na virada do dia UTC o portão nascia vermelho por construção e a rodada nunca chegava a girar o bloco) → `doctor.js --offline` (para tudo se houver erro, e a rodada fecha vermelha) → teto diário **e** distância mínima da última publicação em `pipeline/cadence.json` (os dois **antes** de escolher pauta) → `pick-lead.js` → `new-post.js` → escreve o `draft.json` seguindo `prompt.md` (o texto é do `write.js` na fila de provedores, e o primeiro da fila é o agente do app via `qodercli`, com as APIs HTTP atrás como reserva) → foto real → `make-cover.js` → `check-post.js` (máx. 3 correções) → `score.js` (para se for duplicata) → `publish.js`. Rodada que passa pela manutenção e não publica ainda chama o `build.js` completo para girar a capa. `tools/` nunca faz push, nunca faz deploy, nunca toca na identidade visual. O push é do runner — `hwp-turno.sh` aqui, a etapa final do workflow no Actions — e só acontece em `main`, nunca com `--force`. Prova do destravamento: `node .audit/teste-trava-picks.js`.

- **Teto de publicação:** `max_publishes_per_day` (hoje 4). Publicar mais que isso em domínio recém-reativado é o perfil exato que os buscadores tratam como fábrica de conteúdo — o teto subiu junto com o relógio, mas a média real medida nos últimos 7 dias ficou em ~1,3 peça/dia porque a fila esvazia antes do teto, e é isso que o aviso `cadence-entrega` do doctor mostra sem fechar a rodada. Para furar o teto uma vez: `node tools/publish.js <slug> --force-cadence`. O furo é decisão sua e continua sendo, mas deixa rastro: o travão que teria barrado (teto do dia e/ou distância mínima) é impresso no console — e portanto no `TURNO.md` — e o registro em `pipeline/memory.json` ganha `forcada: true`, que `doctor.js` conta nos últimos 7 dias como aviso `cadence-override`. Antes disto, duas de três publicações de um mesmo dia tinham entrado furadas e nada no repositório dizia isso depois. Prova: `node .audit/teste-furo-cadencia.js`.
- **A meta é conferida contra a agenda, não contra a vontade:** `tools/lib/schedule.js` lê o cron do `.github/workflows/turno.yml`, aplica `min_hours_between_publishes` e devolve o máximo de publicações que aquele relógio entrega num dia de 24h. O `doctor.js` fecha **vermelho** se `max_publishes_per_day` passar desse número, se o `cron_expression` do JSON divergir do cron do workflow, e avisa se `checks_per_day` ou `check_hours` não baterem com o cron no fuso declarado. É por isso que o workflow continua no repo desabilitado em vez de apagado: o par régua×agenda que o portão confere é o **arquivo**, e o `OnCalendar` do timer local foi escrito para bater com ele (08/12/16/20 no fuso = 11/15/19/23 UTC). Foi essa conta que mostrou o primeiro buraco: com os horários antigos (07/10/14/17/21 UTC, dos quais 07/10/17 **nunca** dispararam no Actions) a agenda permitia 4 publicações contra uma meta declarada de 5 — verde dia após dia sem publicar nada.
- **Distância entre publicações:** `min_hours_between_publishes` (hoje 3). Sem ele, duas rodadas perto da meia-noite UTC publicavam no mesmo dia com 43 minutos de diferença. É checado **antes** de escolher a pauta e **vale depois da virada do dia UTC**: com uma peça às 21h, as rodadas da manhã seguinte pararão cedo em vez de percorrer brief + texto + editor para serem barradas no `publish.js`. Se o `pipeline/memory.json` estiver ilegível, o gap cai no histórico dos commits `publish:` — a trava não abre junto com o teto.
- **A memória do robô: `pipeline/memory.json`.** Versionada, é a única coisa que sobrevive entre rodadas **em qualquer máquina** (`drafts/`, `leads/` e o resto de `state/` são gitignored e nascem vazios num clone novo — aqui nesta elas persistem, no Actions não; `cover-state.json` e `hero-fallback.html` são as exceções versionadas, porque sem eles a troca de capa perde a memória e a capa manual some). Guarda, por URL de fonte normalizada (`utm_`, barra no cabo, âncora, http→https — o caminho continua sensível a maiúsculas, porque no servidor ele é), o resultado de cada tentativa — `em_andamento`, `falha_brief`, `falha_texto`, `falha_publicacao`, `fonte_inalcancavel`, `reprovada`, `publicada` — e a lista das publicações com data. É o que o teto lê e o que impede a mesma pauta de ser reescolhida três rodadas seguidas. Janela de re-tentativa por resultado em `lead_retry_hours`; `publicada` nunca volta.
- **Dois relógios no mesmo minuto é vermelho antes de começar.** O cron local e o do arquivo coincidem de propósito, então se o workflow for reabilitado na aba Actions as duas mãos escrevem em `pipeline/memory.json` — a mesma pauta marcada `em_andamento` duas vezes, duas rodadas queimando a mesma fonte. O portão está no `hwp-turno.sh`: uma prova local (`~/.local/state/hwp/actions-desligado`, criada por você depois de desabilitar) barra a ausência, e a API pública do GitHub — lida para arquivo e parseada sem engolir erro — barra a reabilitação feita depois da prova. Falha de rede não barra (o site não pode calar por isso); o que barra é o `active` confirmado. A primeira versão desse portão tinha um `SyntaxError` atrás de um `2>/dev/null || echo desconhecido` e falhou aberto em toda rodada: por isso o stderr agora é impresso.
- **Há um terceiro relógio possível, e ele é o app.** O Qoder desta máquina tem uma automação própria ("Homeworld Press — turno editorial 2x/dia", cron `23 12,20` no fuso de Brasília, `bypassPermissions`), que coincide de minuto com o timer nas duas horas da tarde/noite. Medido em 13/11 às 20:23: o card rodou 5min16s, `file_changes_json` vazio — leu a árvore, viu o `TURNO.md` sujo da rodada manual, conferiu a cadência e parou sem escrever nada — enquanto o `hwp-turno.service` do mesmo minuto morria vermelha no portão da árvore. Nenhum dos dois publicou, nenhum dos dois estragou o repo, e é exatamente esse o custo de ter dois: o plano do app gasto duas vezes para o mesmo resultado. O redator já é o Qoder (`qodercli`, tipo `cli` em `providers.json`); o card é o Qoder despertando a si mesmo. Pausar a automação do app é decisão do dono, não deste arquivo — `tools/` não alcança o banco do app, e escrever nele seria estragar estado de outra aplicação. Uma fonte de 24 dias não é notícia; era isso que entrava no ar quando a nota vinha de palavra-chave e não de frescor. Sem data legível no feed, a pauta **não** é descartada.
- **Idade da pauta:** `lead_max_age_days` (hoje 7). Uma fonte de 24 dias não é notícia; era isso que entrava no ar quando a nota vinha de palavra-chave e não de frescor. Sem data legível no feed, a pauta **não** é descartada.
- **Anti-duplicata tem três portas,** todas com a mesma definição em `tools/lib/memory.js`: a URL da fonte já citada por matéria no ar (`pick-lead`, `ingest`, `check-post`), o título da fonte já citada — pega coluna recorrente, que sai toda semana com URL nova (`pick-lead`) — e a quase-duplicata de texto calculada por `score.js`.
- **Painel:** `node tools/admin.js` sobe em `http://127.0.0.1:8099` (só nesta máquina). Mostra estado, rascunhos com veredito, pautas com botão de brief, ranking com badge de capa, ajuste manual de nota e os últimos logs. Os botões chamam os mesmos scripts; o PUBLICAR só habilita com check verde.
- **Para pausar o robô:** `systemctl --user stop hwp-turno.timer` (pausa o relógio; `start` volta, e `Persistent=true` refaz no boot a rodada perdida enquanto ele ficou parado — se você quiser o silêncio mesmo, `disable --now`) ou mude `max_publishes_per_day` para 0 — as verificações continuam, a publicação para. O `--now` importa: `disable` sem parar deixa o timer rodando até o próximo elapse.
- **Contabilidade alta e clara:** se o commit `publish:` local falhar, `publish.js` escreve `AVISO:` e `turno.js` fecha a rodada em vermelho. Uma rodada que publica sem registrar é pior que uma rodada que não publica, porque o teto do dia seguinte lê 0/2 e o robô repete a fonte. Se o *registro* em `pipeline/memory.json` estourar, o `publish.js` desfaz a publicação inteira (catálogo, HTML, sitemap, notas, memória e last_runs) e sai vermelho — porque o último passo do workflow faz `git add -A` mesmo em rodada falha, e um artigo no ar sem contabilidade seria empurrado com o rótulo `turno:`.

### Se o GitHub Actions voltar a ser o relógio

O workflow `.github/workflows/turno.yml` está **desabilitado** desde 13/11, mas não foi apagado: o cron dele é a agenda que `tools/lib/schedule.js` e o doctor conferem contra `cadence.json`, e ele guarda as chaves em **Settings → Secrets** — reabilitar é o caminho de volta se a máquina ficar ligada apenas algumas horas por dia, que é o risco real de um portátil como relógio. Antes de reabilitar, desligue o timer daqui (`systemctl --user disable --now hwp-turno.timer`) e apague a prova local (`rm ~/.local/state/hwp/actions-desligado`), senão o portão do `hwp-turno.sh` e o cron do arquivo disparam os dois no mesmo minuto. O que o runner da nuvem faz de diferente:

- **O cron é UTC e é *best-effort* — e foi isso que moveu o relógio para cá.** Medido em 41 rodadas (out–nov/2026): o scheduler do GitHub Actions free tier entrega apenas **2 das 6 rodadas agendadas por dia**, e os outros 4 slots somem silenciosamente, sem aviso. O cron original (`23 3,7,11,15,19,23 * * *`) chegou reduzido a `23 15,23 * * *`; hoje o arquivo declara `23 11,15,19,23 * * *` (= 08:23, 12:23, 16:23 e 20:23 em Brasília) porque **quem entrega as quatro é o timer local**, que tem `Persistent=true` e refaz no boot a rodada perdida. Minuto 23, fora da fila das horas cheias; 4h entre horários contra 3h de distância mínima, o que tolera até 1h de atraso sem que a rodada seguinte seja barrada pela distância. Rode agora quando quiser com `systemctl --user start hwp-turno.service`.
- **Provedores de texto: `pipeline/providers.json`.** O arquivo lista os provedores *na ordem em que devem ser tentados*. Desde 13/11 o primeiro é **`qoder`, tipo `cli`**: quem escreve é o agente do app, chamado pelo mesmo `write.js` como subprocesso (`qodercli -p --no-session-persistence --tools ""`), com o `prompt.md` entrando pelo stdin e a resposta saindo como texto puro — sem ferramentas, então o redator não tem como escrever arquivo nem rodar comando; o `draft.json` continua sendo gravado pelo `write.js`. O modelo vem de `fila`: hoje `["Efficient"]`, que vira `-m Efficient` e é o modo que o plano grátis paga — **sem `fila`, o CLI usa o padrão dele (`Auto`), e Auto é o que cobra crédito**. Os nomes válidos são os de `qodercli --list-models`. Ele não tem chave: entra na fila se o binário existe, procurado em `bin` → `$QODER_CLI` → o mais novo em `~/.qoder/bin/qodercli/` → PATH (o app se atualiza trocando o nome do arquivo, então caminho fixo não é régua). Os demais são HTTP e ficam inertes sem chave: o JSON diz o **nome** da variável (`chave_env`), nunca a chave — no Actions é o Secret, aqui é o `.env` da raiz lido por `tools/lib/load-env.js`, que **não sobrescreve** o que já está no ambiente (o Secret ganha se o workflow voltar). Provedor armado mas fora do ar é pulado; provedor que responde 503/429 é esperado e tentado de novo; provedor que recusa (chave inválida, nome morto) é descartado e a rodada passa para o próximo. Prova do tipo `cli`: `node .audit/teste-provedor-cli.js` (24 conferências — a ordem de localização do binário, o provedor ficando inerte quando ele some, o `-m Efficient` chegando na linha de comando e o `-m` ausente quando a fila não declara modelo, as quatro saídas do subprocesso, o hang morrendo no teto de parede e os HTTP de reserva intactos).
- **Trocar de redator é uma linha, não um patch.** Enquanto o plano do app é grátis, `qoder` escreve e os HTTP ficam inertes. Se o plano mudar: `"ativo": false` no `qoder` e uma chave no `.env` — `node tools/write.js --check` diz quem ficou armado antes da rodada decidir. O risco novo dessa escolha é real e tem nome: a rodada passa a depender de cota e do login do app nesta máquina, e o `OnCalendar` não sabe se a sessão expirou. É por isso que o binário ausente não derruba a rodada no passo 7 com a pauta queimada: o pré-voice do runner vê `armados() === 0` e recusa começar, e o `chamar` do tipo `cli` traduz "cota esgotada" em 429 — transitório, que é como o `write.js` trata provedor ocupado.
- **O segredo de escrever é `tools/write.js`**, que não tem lista fixa de modelos: pergunta a cada chave quais existem (`GET .../models`), ordena por versão, e quando a API do Google responde "use models/X", segue a dica. Nome de modelo aposentado não derruba mais a rodada.
- **Diagnóstico sem gastar rodada nem cota:** `node tools/write.js --check` mostra quem está armado, quem está sem chave e a fila de modelos de cada um. Zero geração.
- **Se a rodada para**, o motivo fica em `TURNO.md` (commitado pelo próprio robô) com uma linha por `provedor/modelo` tentado. O commit do relatório roda com `if: always()`.
- **Rodada vermelha não sobe matéria ao ar.** O mesmo `if: always()` é o risco: ele faria `git add -A` em qualquer resíduo deixado no diretório e a matéria entraria com o rótulo `turno:`, sem commit `publish:` e sem contabilidade. Antes do `add`, se a etapa da rodada não terminou `success`, o workflow recua TUDO para o HEAD (`git checkout HEAD -- .` + `git clean -fdq`) e devolve ao lugar só os dois arquivos de registro — `TURNO.md` e `pipeline/memory.json`, que dizem o que a rodada tentou e travam a reoferta da mesma fonte. Recuo geral em vez de lista de caminhos: uma saída nova de qualquer ferramenta não escapa por esquecimento. Como o `publish:` legítimo já virou HEAD, a matéria publicada de verdade continua no ar — só o que ficou pela estrada é descartado. `TURNO.md` e `pipeline/memory.json` seguem sendo commitados: é o registro do que a rodada tentou. Consequência conhecida e aceita: a troca de capa que o `girarCapa()` do `turno.js` acabou de escrever (`index.html` + `cover-state.json`) também volta, então **rodada vermelha não serve rodada** — a meta de `cover_changes_per_day` (4, uma por horário do `check_hours`) vale para as rodadas que terminam verdes. Não é buraco de régua: o site no ar nunca viu aquela capa, porque nada foi empurrado. O mesmo recuo leva o bloco do Today's Picks que o `build.js --daily` do passo 2 acabou de girar — e não reabre o travamento, porque a rotação diária roda ANTES da manutenção: na rodada seguinte o bloco é regerado para o dia dela antes de o doctor conferir.
- **Push = deploy.** O runner commita `TURNO.md` e o que a rodada mudou; a Vercel publica a cada push em `main`. Não existe mais passo manual de upload (ver [PUBLISHING.md](PUBLISHING.md)) — nem aqui: o push é do `hwp-turno.sh`, nunca de uma linha sua e nunca de dentro de `tools/`.
- **Conflito de push resolve-se sozinho só onde é seguro.** Se outro commit entrou durante a rodada, o runner faz `git pull --rebase`; se o rebase parar por conflito, ele favorece o da rodada **somente** nos arquivos que o próximo build regenera do zero (`TURNO.md`, `pipeline/state/*`, HTML de índice/artigo, `sitemap.xml`, `vercel.json`, `a-*.html`, `r-*.html`). Catálogo, `pipeline/memory.json` e `pipeline/scores.json` continuam bloqueando: o `-X theirs` global que existia aqui resolvia a capa e, no mesmo golpe, jogava fora o hunk do outro lado — ou seja, uma matéria já publicada ou o registro que o teto lê. Conflito nesses caminhos fecha a rodada vermelha com `git status` no log, para resolver à mão. A regra é a mesma nas duas mãos: o `hwp-turno.sh` repete a lista de regeneráveis e, antes de qualquer coisa, recusa `--force` e histórico divergente.

#### Armar um segundo provedor (quando quiser)

Hoje estão armados o **Gemini** (`GEMINI_API_KEY`) e a **NVIDIA** com duas chaves (`NVIDIA_API_KEY` e `NVIDIA_API_KEY_2`). A NVIDIA grátis anuncia o catálogo inteiro em `/v1/models` mas libera só parte dele por conta — modelo fora da sua cota responde `404 Function not found for account`, então a fila lista só o que foi testado de verdade: `openai/gpt-oss-20b` e `minimaxai/minimax-m3.1-flash`. Os dois são modelos que "pensam": gastam tokens no raciocínio antes de escrever, daí o `max_tokens` mais alto no JSON.

Para acrescentar outro provedor, sem tocar em código:

1. Crie a conta no provedor e gere a chave (`console.groq.com`, `cloud.cerebras.ai`, `console.mistral.ai`, `openrouter.ai`). Os quatro falam o mesmo dialeto (`/chat/completions`), por isso o mesmo adaptador serve para todos. Confira no site o limite gratuito do dia — ele muda sem avisar.
2. Guarde a chave onde o relógio procura: nesta máquina, uma linha `NOME_DA_CHAVE=...` no `.env` da raiz do repositório (gitignored; edite você mesmo — a chave não passa pelo chat). Se o Actions voltar a ser o relógio, o lugar é **Settings → Secrets and variables → Actions → New repository secret**. O nome tem de ser exatamente o `chave_env` de `pipeline/providers.json` (`GROQ_API_KEY`, `CEREBRAS_API_KEY`, `MISTRAL_API_KEY` ou `OPENROUTER_API_KEY`). Os dois caminhos chegam ao mesmo lugar: `tools/lib/providers.js` chama `tools/lib/load-env.js`, que põe o `.env` no ambiente **sem sobrescrever** o que já estava lá — Secret do Actions ganha sempre.
3. Rode `node tools/write.js --check` com a chave no ambiente para ver a fila que ele usaria. Não gera texto, não gasta cota.
4. Nada mais. No próximo turno o provedor entra na fila na posição em que está no JSON; se o de cima falhar, o de baixo escreve e o `TURNO.md` dirá `escrito por nvidia/openai/gpt-oss-20b`.

Para inverter a ordem, basta trocar as linhas do arquivo (`peso` decide quanto tempo da rodada cada um recebe). Para desligar um provedor sem apagar a chave, `"ativo": false`.

Se um modelo responder JSON incompleto, o `write.js` grava a resposta recusada em `pipeline/drafts/<slug>/rejeitado-<provedor>-<modelo>.txt` — é ali que se vê o que ele escreveu de errado.

## O que continua dependendo de gente

- **Domínio.** O site está no ar em `site-homeworldpress.vercel.app`, mas os canonicals de todas as páginas apontam para `homeworldpress.com` — e esse domínio ainda responde com a página de estacionamento do GoDaddy. Enquanto os nameservers não forem trocados no DomainControl, o Google vê um canonical que não é o site. Passo a passo em [PUBLISHING.md](PUBLISHING.md).
- **Conta Amazon Associates.** Sem a sua Store ID real, os 184 links com a tag `homeworldpres-20` não rendem nada. Depois de aprovado, a troca é `node tools/set-affiliate-tag.js <sua-tag>` (acima).
- **"Nós testamos."** Só sai da sua mão. Sem aparelho na mão, o texto é comparação de especificações e precisa se chamar isso.
- **Fotos de produto.** As imagens do review de e-readers são Unsplash, e algumas não batem com o produto (tem luminária ilustrando um Kindle Scribe).
- **Direito de imagem de capas.** As capas históricas da editora vêm do arquivo do James Gauthier; antes de publicar, confirme a permissão por escrito.
- **Medição de tráfego.** Hoje não há nenhuma: escolher entre Google Search Console (o dado que decide a estratégia de afiliado) e um script de analytics é decisão sua.
- **Nota manual no painel.** Opcional. Serve para corrigir o robô quando ele erra de julgamento, não para substituí-lo.
