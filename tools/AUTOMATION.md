# Automação — as três camadas

Node puro: sem npm, sem dependência, sem serviço pago. As chaves de API usadas são a do Gemini/NVIDIA (free tiers, só pela Camada 3) e a do Unsplash (`UNSPLASH_ACCESS_KEY`, para achar foto real). Rodam na sua máquina com o Node que já existe (v24). Desde 13/11 a Camada 3 também roda **aqui** — é o timer `hwp-turno` quem dispara e empurra a rodada; o `.github/workflows/turno.yml` continua no repo como a agenda que o doctor confere, mas está **desabilitado** na aba Actions.

```bash
node tools/doctor.js            # varredura completa (inclui links externos)
node tools/doctor.js --offline  # sem rede: assets, metadata, catálogo, sitemap
node tools/doctor.js --quick    # só catálogo + assets + metadata
node tools/ingest.js            # atualiza a fila de pautas
node tools/ingest.js --show     # imprime a fila de hoje
node tools/build-sitemap.js     # regenera sitemap.xml a partir do catálogo
node tools/build-dist.js        # monta dist/ para upload (ver PUBLISHING.md)
```

## `doctor.js` — o que ele pega sozinho

| Checagem | Erro quando |
|---|---|
| `asset-missing` | arquivo referenciado em HTML/DB não existe no disco |
| `asset-not-image` | `.jpg`/`.png` que na verdade é HTML salvo (foi assim que o `toyman_cover.jpg` quebrou) |
| `internal-link` / `anchor` | link interno não resolve, âncora sem alvo |
| `date-rot` | data relativa tipo "2 HOURS AGO" no catálogo |
| `meta-*` | página sem title/description/canonical/og:image/favicon; 404 sem `noindex` |
| `a11y-input` | `<input>` sem label |
| `sitemap-drift` | artigo publicado ausente do sitemap |
| `feed-stale` | o `feed.xml` commitado não é exatamente o que `build-feed.js → buildItems()` escolhe hoje (matéria nova fora do RSS — foi assim que o feed ficou parado no Hubble por cinco publicações com o robô verde) |
| `cadence-override` | publicação dos últimos 7 dias marcada `forcada:true` em `pipeline/memory.json` (aviso: alguém furou o teto com `--force-cadence`, e agora isso é contável) |
| `repetition` | dois artigos publicados abrindo com as mesmas palavras, ou com o mesmo padrão rítmico |
| `orphan` | matéria ou review que nenhuma OUTRA página tem link para ela (a própria página é o destino, não a entrada) |
| `affiliate` | link Amazon/Audible sem `tag=`, ou tags inconsistentes entre si |
| `cover` | `cover_changes_per_day` ≠ número de horários do `check_hours`, `cron_expression` ≠ workflow, nenhuma matéria acima do piso da capa, ou acervo sem para onde girar |
| `picks` | `picks_changes_per_day` ≠ 1, slot sem `"rotacao": "dia"`, pool abaixo do mínimo para trocar todo dia, o par publicado ≠ o par que a régua de hoje calcula, card `pick-item` fora dos marcadores, picks repetindo a capa ou sem artigo no catálogo |
| `placeholder-copy` | texto de rascunho visível ao público (ex.: o bloco "ADVERTISEMENT // …") |
| `external-broken` | link externo devolvendo 404/500 |
| `external-blocked` | 401/403/406/429 — provável bloqueio a robô, abre manualmente (aviso, não erro) |

Saída: console + `tools/reports/AAAA-MM-DD.md`. Código de saída `1` quando há erro — é isso que o agendador usa para saber que algo mudou.

## `ingest.js` — de onde vêm as pautas

12 feeds públicos gratuitos (Publishers Weekly, Reactor, Guardian SF, Publishing Perspectives, SFWA, Ars Technica, The Verge, Hacker News, Science Daily, Phys.org, Space.com). Nenhum exige cadastro.

Cada item é pontado pelos vocabulários dos 5 pilares, descartado se parecer tema já publicado, deduplicado por título e limitado a 8 pautas por fonte. O resultado vai para:

- `pipeline/leads/AAAA-MM-DD.json` — estrutura para consumo por script
- `pipeline/leads/AAAA-MM-DD.md` — a mesma fila legível, com pilar, registro sugerido e url
- `pipeline/state/seen.json` — URLs já vistas (últimas 4000). **Só vale na sua máquina**: `state/` é gitignored (com duas exceções versionadas, abaixo), então num runner limpo ele nasce vazio todo turno. O que impede a fila de repetir o que já está no ar, em qualquer lugar, é `pipeline/memory.json` + as fontes do catálogo (ver Camada 3).
- `pipeline/state/cover-state.json` e `pipeline/state/hero-fallback.html` — **versão no git**, porque a memória da capa tem de sobreviver a um runner limpo: sem `cover-state.json` cada rodada acordaria acreditando que nunca trocou a capa, e sem o fallback a capa escrita à mão sumiria do `index.html` no primeiro build.

Cada pauta traz `pillar`, `register` e `fit`. Isso é o insumo da Camada 2: quando você quiser escrever, a pauta já vem com o encaixe editorial decidido — mas a decisão de escrever continua sua.

O que o `ingest.js` **não** faz: não acessa a Amazon, não verifica preço, não confirma fato, não escreve.

## Agendar nesta máquina (uma vez, sem instalar nada)

Desde 13/11 o relógio do site **é** esta máquina: `~/.config/systemd/user/hwp-turno.timer` dispara `~/.local/bin/hwp-turno.sh`, que espelha os passos do workflow e termina em `node tools/turno.js` + commit `turno:` + push. O workflow do Actions está desabilitado, e o script se recusa a começar sem a prova local de que ele foi desligado (`~/.local/state/hwp/actions-desligado`) — dois relógios no mesmo minuto escreveriam em `pipeline/memory.json` ao mesmo tempo.

As duas unidades estão fora do repositório de propósito: a proibição do AGENTS.md é *nenhum script de `tools/` chama push*, e quem empurra é o operador, não o repo. Conferir e mexer:

```bash
systemctl --user list-timers 'hwp-*'      # próxima elapse do turno e do vigia
systemctl --user start hwp-turno.service  # rodada agora, pelo caminho inteiro
journalctl --user -u hwp-turno.service -n 50   # o que a última rodada disse
tail -20 ~/.local/state/hwp/avisos.log    # o que os portões avisaram (verde e vermelho)
touch ~/.local/state/hwp/actions-desligado     # só depois de desabilitar na aba Actions
```

O log é `~/.local/state/hwp/turno.log` (`StandardOutput=append:` do serviço), porque o `TURNO.md` commitado é a versão pública da mesma sequência. Diferenças que importam contra o runner da nuvem: o script **recusa árvore suja** antes de tocar em qualquer arquivo (o recuo geral da rodada vermelha é `git checkout HEAD -- .`, e num clone descartável isso é seguro; na sua máquina apagaria trabalho seu), e `Linger=yes` + `Persistent=true` existem para a rodada perder o horário e ainda assim ser feita no boot seguinte, em vez de sumir do dia — que era o defeito medido do scheduler do Actions.

### Quem avisa, e quem confere se o aviso era preciso

Ninguém abre `turno.log` todos os dias, e um relógio que é um portátil falha calado: tampa fechada, bateria no fim, rede fora do ar. Duas unidades a mais moram fora do repo por isso:

- **`~/.local/bin/hwp-aviso.sh <origem> <mensagem>`** é a boca única. Escreve em `~/.local/state/hwp/avisos.log` **sempre** — é o registro que sobrevive — e tenta `notify-send` na área de trabalho, cujo fracasso é silencioso por desenho (sem sessão gráfica não há notificação, mas a linha fica). O `hwp-turno.sh` chama o aviso em toda saída vermelha (árvore suja, sem rede, dois relógios, redator desarmado, commit ou push que não passaram) e, na verde, quando o contador de publicações do dia subiu — a conta é `lib/cadence.publishedToday()`, a mesma função que o teto lê, não um palpite sobre o `TURNO.md`.
- **`hwp-vigia.timer`** (uma olhada por hora, às :41 — nunca no minuto da rodada) roda `~/.local/bin/hwp-vigia.sh`, que lê a régua de `pipeline/cadence.json` e pergunta o que o doctor não pergunta: **a rodada do horário aconteceu?** A resposta vem de um cabeçalho `===== turno local …` no `turno.log`, com 90 min de folga (o `AccuracySec`, as 3 tentativas de rede e os 65 min de timeout do turno no runner, mais os ~10 min de git que o runner ainda faz depois dele). O cabeçalho é escrito no **começo** da rodada, então ele prova que a rodada abriu, não que serviu: o vigia lê o bloco entre aquele cabeçalho e o próximo e, se houver `VERMELHO` ali, o aviso é **"rodada vermelha"**, com a causa escrita naquele bloco. Medido em 13/11: às 20:23 a rodada abriu, morreu no portão da árvore e o vigia cantou "servida e empurrada" — a mesma família do teto cego e da capa parada. A outra metade do defeito apareceu em 14/11: quando quem barra é o próprio `tools/turno.js`, a causa moria no exit code e não havia token nenhum no bloco (duas rodadas sem texto, zero publicações, aviso verde) — desde então o `finish()` imprime `VERMELHO: <causa>` em toda saída não-zero, e é essa linha que o vigia passa a ler. Terceiro buraco, também de 14/11: na virada do dia, antes do primeiro horário, o slot cobrado era o **primeiro de hoje** — o aviso das 00:41 gritou "a rodada das 2026-11-13 08:23", um horário que nunca tinha chegado. Agora, sem horário vencido hoje, a régua ordenada devolve o **último de ontem**. Depois pergunta se ela chegou ao ar: `origin/main..HEAD` com commit local à frente é a peça escrita que o site não vê. E confere o fuso: o `OnCalendar` corre no fuso **do sistema**, enquanto `check_hours` declara um fuso — divergindo, os horários do timer não são os da régua, e o doctor continua verde porque ele compara o JSON com o cron do arquivo. A quarta boca era o **verde emprestado**: falta de `VERMELHO:` no bloco também não prova que a rodada terminou, e o `timeout` do runner corta o `turno.js` no meio sem escrever fim nenhum — o vigia lia cabeçalho + nenhuma falha e cantava "servida e empurrada" com o diário truncado. Desde 15/11 ele exige uma das bocas de fechamento (`push ok`, `nada para commitar`, `push recusado`) dentro do bloco para declarar a rodada entregue; sem elas o aviso é `rodada sem desfecho`, que é exatamente o que um `SIGKILL` do `TimeoutStartSec=78min` deixa para trás. O `VERMELHO:` da mão barrada no `flock` (a que chegou no minuto da outra e não escreveu nada) é filtrado antes de qualquer leitura do bloco, senão ele mascara o desfecho da rodada que serviu; e `push pendente` só dispara em bloco **sem** `push ok` — com duas mãos no relógio, um commit local à frente pode ser da rodada que ainda vai chegar, e isso não é peça que o site não vê. Prova: `node .audit/teste-vigia-local.js` (105 conferências; contra o script anterior ao portão, 15 delas ficam vermelhas).
- Uma rodada perdida ou vermelha é avisada **uma vez** (`~/.local/state/hwp/vigia-ultimo` guarda o slot já cobrado), para o vigia não virar spam de hora em hora. Cada aviso leva a própria etiqueta no `avisos.log` — `rodada perdida`, `rodada vermelha`, `push pendente`, `fuso` — porque as quatro são defeitos diferentes com a mesma caixa de notificação.
- O portão da árvore do runner perdoa **um** arquivo: `TURNO.md` sozinho é o diário que o próprio runner commita em toda rodada, e uma rodada à mão (`node tools/turno.js`, o caminho manual do AGENTS.md) deixa exatamente ele sujo. Com mais qualquer caminho na árvore, a rodada para como sempre parou — perdoar o diário não é apagar trabalho do dono.

Prova do vigia: `node .audit/teste-vigia-local.js` (53 conferências — servida e empurrada muda, rodada já encerrada em VERMELHO avisa dentro da folga e a mutação que tira o atalho a engole outra vez, rodada perdida avisa uma vez e não avisa de novo, rodada vermelha avisada com a causa sem cantar verde, o vermelho de um horário antigo não mancha o verde do seguinte, push pendente contado, fuso divergente, slot dentro da folga calado, a virada do dia cobrando o último horário de ontem (e a chave gravada sendo essa mesma), e nada do teste escreve no estado real da máquina). Prova do portão da árvore: `node .audit/teste-runner-portao.js` (18 conferências — o runner real roda contra um fixture no /tmp pelas bocas `HWP_REPO`/`HWP_STATE`/`HWP_AVISO` e para em `HWP_SO_PORTAO`, que é a única parte dele conferível sem queimar uma rodada no repo de verdade).

`pipeline/drafts/`, `pipeline/leads/`, `pipeline/state/seen.json` e `tools/reports/` são gitignored mas **persistem aqui**, o que não acontece no runner: lá cada rodada acordava com a fila de vistos vazia. A régua de repetição continua sendo `pipeline/memory.json` + as fontes do catálogo, que são versionadas e valem em qualquer lugar.

## Publicação de posts (Camada 2)

Quatro comandos. O passo de escrever o texto pode ser seu (colar `prompt.md` no chat) ou do robô agendado (Camada 3):

```bash
node tools/ingest.js                 # fila de pautas (camada 1)
node tools/new-post.js 3             # pauta nº 3 → pipeline/drafts/<slug>/{brief.json,prompt.md}
#   quem escreve: você, ou o turno agendado, seguindo prompt.md à risca
node tools/make-cover.js <slug>      # só para matéria SEM foto real: placa SVG → images/covers/<slug>.svg
node tools/check-post.js <slug>      # editor mecânico → review.md, exit 1 se reprovar
node tools/score.js --draft <slug>   # nota 0–10 calculada por rubrica (não é opinião)
node tools/publish.js <slug>         # só com check verde: catálogo + capa + feeds + sitemap + commit
```

- `pick-lead.js` só entrega pauta cuja fonte abre agora: feed de notícia às vezes publica item com link morto, e o editor mecânico reprova link 404 depois que o texto já custou chave. Pautas descartadas saem no stderr.
- `new-post.js` monta o brief no formato exato do input contract de `voice/WRITER_PROMPT.md`, escolhe a byline pelo território (`EDITORIAL_VOICE.md` §4) e embute a memória anti-repetição de `voice/state/last_runs.json` no prompt.
- `make-cover.js` desenha a miniatura sem banco de imagens e sem custo: placa 1200×675 em SVG, com a cor do pilar (a mesma de `css/styles.css`), o kicker e o título quebrado em até 4 linhas. É determinística — mesmo slug, mesma placa — e só preenche `image`/`imageAlt` quando o draft ainda está sem capa. O turno roda ela de novo depois de cada reescrita, porque o modelo devolve `image: null` e `write.js` preserva a capa anterior. **Matéria que já tem foto real (`images/posts/*.jpg`) sai dela com exit 0 e nenhuma placa gerada** — era exatamente esse `exit 1` que, desde 05/11, abortava todo `publish.js` de matéria com foto: o turno chamava a placa depois de a foto já estar no draft, a placa falhava, e o `publish.js` desfazia a publicação inteira.
- **Foto real é portão, não enfeite:** antes de inserir no catálogo, `publish.js` exige `image` (ou `bookCover`) apontando para `.jpg`/`.png`/`.webp` que não seja placa. Sem foto, chama `tools/find-cover.js` (busca em `tools/lib/find-photo.js`: Unsplash → Pexels), salva em `images/posts/<slug>.jpg` e grava crédito e autor no draft. Se nenhum candidato achar foto, a publicação **aborta** (exit 1, catálogo intacto) e `tools/notify-foto.js` abre uma issue no repositório com o log da busca — porque rodada abortada em silêncio foi exatamente como o site passou três semanas sem publicar.
- **De onde sai a foto (régua de 07/11):** a primeira query é o campo `photoQuery` do rascunho — 3 a 6 palavras em inglês nomeando a CENA que a foto deveria mostrar, escritas por quem escreve o texto. `check-post.js` reprova rascunho sem ele (gate `photo-query`), porque a query montada a partir da manchete já colocou no ar um render de "QUANTUM" numa matéria de íons presos: "two trapped ions let a gauge field" não é vocabulário de banco de imagem. O numeral e a palavra vazia são riscados da query por `palavrasConcretas()`, a mesma régua que o portão usa. E a foto deixada de fora do catálogo não é mais `results[0]`: pedem-se 5 candidatas e escolhe-se a cuja legenda (`alt_description`) aparecem palavras inteiras da query — prova de assunto que existe sem ver a imagem; empate se decide por curtidas. Se nenhuma das 5 legendas menciona a query, o candidato é recusado com motivo e a busca passa para a próxima query; esgotadas as queries, aborta como acima. `node .audit/teste-foto-query.js` (offline, fetch falso) e `node .audit/muta-foto-query.js` (desliga cada regra e exige teste vermelho) são a prova disso.
- `check-post.js` mede tudo no texto, não confia no `self_check`: tags permitidas, vocabulário banido (lista única em `WRITER_PROMPT.md`), templates estruturais (máx. 1, nenhum como fecho), ritmo (frase ≤30 palavras, frase curta obrigatória, 1 parágrafo de uma frase, 1 parágrafo longo — tudo medido **dentro do bloco**: `</p>`, `</li>`, `</h2>`, `</h3>`, `</blockquote>` são a fronteira, e um `<h2>` sem ponto final não entra na conta da frase seguinte. Até 15/11 havia duas segmentações no mesmo arquivo, e a de `longest` media o texto inteiro descascado: título+frase viravam uma "frase de 33 palavras" que reprovava a peça e tirava 0,15 do `craft` na nota. Prova: `node .audit/teste-ritmo-uma-segmentacao.js`), humor ≤2 e zero em pauta de morte, abertura/fecho diferentes da última peça do registro, fontes alcançáveis, links do texto presentes nas fontes, comprimento (abaixo de 70% do alvo da pauta é reprovado — o piso é `tools/lib/word-floor.js`, uma régua importada pelo editor, pelo teto do redator e pela linha do contrato no `new-post`. Até 15/11 eram duas contas do mesmo 70%: `write.js` pedia `round(alvo*0.7)` e o `check-post` reprovava abaixo de `ceil(alvo*0.7)` — para alvo 1002, 701 contra 702. O redator entregava 701 achando que passava, o júri cortava em `[length]` e as três tentativas do laço morriam na mesma aritmética: texto reprovado por régua, não por editor), e a regra dura: **"we tested" só com `products[].tested=true` e protocolo em `test_notes`**.
- **O laço de correção é do `turno.js`, não do `check-post.js`.** Reprovado, o turno grava as reprovações em `pipeline/drafts/<slug>/fix.md` e chama o `write.js` de novo (até 3 vezes). Duas coisas desse laço custaram rodadas e hoje têm porta. (1) A ordem colada no prompt é proporcional ao que falta: abaixo do piso (70% do alvo) pede expansão, acima dele pede *corrigir e devolver o mesmo JSON, do mesmo tamanho* — porque "acrescente até 770 palavras" em cima de um texto que já tinha 1146 reescrevia o artigo inteiro e estourava os 780 s do `chamada_max_ms` (rodada das 02:23 de 15/11: uma frase de 33 palavras reprovada, zero peças no ar). (2) Se quem não entrega no laço é o próprio redator, a pauta sai por `falha_texto` (24 h) e a rodada fecha vermelha com as últimas oito linhas do stdout dele no diário — não por `reprovada` (72 h), que é a pena de quem entrega texto reprovado três vezes. (3) `pipeline/drafts/<slug>/fix.md` é resposta AO prompt no disco: o guard de idade do `write.js` ignora um fix mais velho que o `prompt.md` (com um segundo de tolerância, porque dentro da rodada ele nasce a segundos do brief), senão a pauta que volta de um `falha_texto` 24h depois herda as reprovações e o texto da tentativa anterior. Provas: `node .audit/teste-reescrita-proporcional.js` (31 conferências) e `node .audit/teste-vermelho-redator.js` (43). (4) Acima do piso de palavras a reescrita tenta primeiro ser **cirúrgica**: o `write.js` cola o texto atual e pede `{"edits":[{"old":"…","new":"…"}]}` (cada `old` literal, único no corpo, 3-30 palavras), com orçamento de `min(150 s, 20% da parede)` e porta de folga de 420 s. Resposta fora do formato, `old` ambíguo ou ausente, ou trocas que levassem o texto para baixo do piso → cai no caminho antigo e devolve o JSON inteiro, com a causa no stderr. Uma frase reprovada deixa de custar a reimpressão de 1044 palavras, que é o que estourava os 780 s. Prova: `node .audit/teste-reescrita-patch.js` (48 conferências; duas mutações — afrouxar a unicidade do `old` e abrir a porta de folga). (5) O `fix.md` não declara formato nenhum: quem decide é o `write.js`, e o `turno.js` escreve "corrija exatamente estes pontos" — duas bocas dizendo ao modelo em que JSON responder é a família do piso de palavras. (6) O veredito de conexão que manda nesse laço (esperar ou passar a vez ao provedor seguinte) vem de `tools/lib/transporte.js`, módulo compartilhado com o `sonda()` do `pick-lead.js`; ver a linha "Recusa de conexão lida como 'modelo ocupado'" na tabela de `AGENTS.md`. Prova: `node .audit/teste-redator-recusa.js` (31 conferências).
- `publish.js` insere no catálogo, roda `build.js` + `build-sitemap.js` + `build-feed.js` + `meta-pages.js` + `doctor.js`, atualiza `last_runs.json` e faz **commit local**. Se qualquer etapa falhar, restaura o catálogo e não publica. Nunca faz push, nunca faz deploy.

### Onde os cards novos aparecem

`tools/build.js` preenche, entre marcadores `<!-- hwp:auto:<slot>:start/end -->`, os feeds listados em `pipeline/placements.json`: o hero, o bloco TODAY'S PICKS, os subfeatures da coluna central, MOST RECENT e os grids de culture/tech/science na home, e o feed das três páginas de editoria. Nos feeds, a região automática só acrescenta no topo os ids que ainda não aparecem no resto da página. O desconto tem três modalidades por slot (`dedup`): arquivo inteiro (o padrão da home, onde os blocos dividem tela), `"prioridade-ineditas"` (páginas de categoria — o feed é o acervo e a ordem é régua: as matérias que a curadoria do topo já mostrou não podem abrir a lista, elas afundam para o fim; com desconto do arquivo o culture-feed ficava em 5 de 8 e o tech-feed em 1 de 8) e `"somente-automatico"` (grade CULTURE — só os blocos automáticos descontam; sem isso as duas matérias do TRENDING // TOP 5 tiravam vaga e a grade fechava com 5, abrindo um buraco de 437px na última linha de uma grade de 3 colunas). Os feeds de editoria trazem ainda `"acervo": true`, que corta o cap: com `limit: 8`, a página de science listava 11 das 15 peças e a de culture 8 das 10 — e as cortadas não eram as mais velhas, eram as que o `slice` alcançava. Duas matérias do catálogo (uma de cada editoria) não tinham nenhum link de entrada em lugar nenhum do site (medido no HEAD em 09/11). A exceção declarada é o bloco de picks (`"rotacao": "dia"`): ali o desconto é só a região do hero, porque picks é bloco de descoberta e a matéria pode, sim, estar também no feed de cultura logo abaixo.

O build tem dois modos. O completo (sem flag) refaz todos os slots, sincroniza os contadores `count_pill` e gira a capa — é o que o `publish.js` chama e o que o `turno.js` chama no fim de uma rodada que não publicou. O `--daily` processa **só** os slots com `"rotacao": "dia"`, pula os contadores e não toca no hero nem em `pipeline/state/cover-state.json`: é o passo 2 da rodada, antes da manutenção, porque o doctor exige o bloco de hoje no ar e o build completo gastaria a única troca de capa da rodada antes de a matéria inédita tomar o hero. `--dry` continua valendo nos dois (mostra sem gravar). Prova de que o `--daily` não encosta na capa: `node .audit/teste-trava-picks.js` — 22 conferências com relógio falsificado, conferindo o hash do `cover-state.json`, o HTML do hero e o resto do `index.html` antes e depois, mais a idempotência de rodar duas vezes. A régua de **rotação** é por rodada: `cover_changes_per_day` (hoje 6) tem de ser igual ao número de horários do `check_hours`, porque **a capa gira em toda rodada do turno**, com matéria nova ou não — a capa é o que mais chama atenção e o hero não pode ficar parado horas a fio entre uma rodada e outra (com os 4 horários antigos o vão da madrugada era de 12h sem troca; com 6 espaçados 4h o maior intervalo parado é uma rodada). A unidade foi a janela (dia 03:00–12:59 / noite 13:00–02:59, 2 trocas/dia) até 2026-11-07; com seis rodadas por dia, a janela conteria três rodadas e a meta cobraria duas. A régua é o log `changes` de `pipeline/state/cover-state.json`, e **só o `build.js` o escreve**: `publish.js` carimbava a rodada como "servida" mesmo quando a matéria publicada não passava do piso e continuava não sendo capa.

A escolha, em ordem (`pickCover(forceChange, noAr)`): **matéria que ainda não passou pelo hero** toma a capa na primeira publicação da rodada (é o caminho de toda publicação nova), e sem inédita acima do piso a rodada **caminha um passo na lista de elegíveis** (`proximaNaRotação`), voltando ao topo no fim do ciclo. As duas faces descartam `noAr`, o card que JÁ está renderizado na região `index-hero` — o mesmo `regionIds[0]` de que o build precisa para o fallback do hero, não uma segunda leitura da página. Sem esse filtro o `pickCover` devolvia a matéria que estava no ar: como `rotacionada` o `registrarCapa` aceitava a non-op e como `do dia` ele ficava mudo, e as duas bocas do mesmo build discordavam na mesma rodada — medido em `a0fa70d` (15/11), quando `teste-capa-rodada.js` fechou 100/104 com o primeiro build mantendo o hero sem registrar e o segundo rotacionando para a inédita e carimbando "capa do dia". Hoje a rotação que devolveria o card em exibição é reportada `mantida` (104/104, com um ciclo de 18 rodadas cobrindo toda elegível do acervo). Medido em 07/11 com três publicações na mesma rodada: a primeira virou capa, a segunda e a terceira saíram `capa mantida` — a trava da rodada vem antes da inédita, então quem publica depois da primeira troca espera a rodada seguinte. É por isso que a novidade é medida por ID (o conjunto `capaVistas`), não por data: `a.date` do catálogo tem granularidade de dia, então "a mais nova do catálogo" não distingue a matéria publicada agora da que a rotação acabou de derrubar — e foi assim que o segundo build da mesma rodada desfazia a rotação, registrando troca sem publicação enquanto o leitor via a capa em ping-pong.

Como o runner chama o build várias vezes por rodada, repetir a capa da rodada não conta como troca — e a trava é dupla: `registrarCapa` só grava se o HTML do hero mudou de verdade **e** se a matéria agora no ar é outra. Sem a segunda condição, um catálogo com uma única matéria elegível "girava" a capa para ela mesma em cada rodada nova e a meta subia sem nada ter mudado na página. Entradas com mais de 14 dias caem do log (`capaVistas` fica: é memória, não histórico). Quem confere a prova no fim é `tools/turno.js`: `capaServiuRodada()` lê o estado do disco e fecha a rodada em vermelho se não houve troca na rodada em curso — inclusive na que publicou, onde quem girou foi o build chamado pelo `publish.js`.

Três consequências disso ficam nos painéis de propósito:

- **Publicação e capa contam dias diferentes.** O teto de publicações é por **dia UTC** (é o dia do commit `publish:` no runner); a meta de capa é pelo **dia do fuso** do instante. Antes, com janelas, a rodada das 00:23 pertencia à noite do dia anterior e o painel mostrava 5/6 num dia que tinha cumprido as seis. Hoje as seis rodadas (02:23, 06:23, 10:23, 14:23, 18:23 e 22:23) caem no mesmo dia do fuso. Às 21h de Brasília os dois dias já são outros — não é bug, é o relógio de cada régua. Consequência que a mudança de agenda trouxe: a rodada das **22:23** é 01:23 UTC, ou seja, publica no dia UTC seguinte, e os cinco horários das 02:23 às 18:23 publicam no dia UTC do próprio fuso. Um dia UTC recebe portanto as cinco peças locais do dia mais a peça das 22:23 do dia anterior — é o teto que decide, não a agenda.
- **A rodada que não publica também gira a capa.** `tools/turno.js` chama `build.js` ao encerrar qualquer rodada que passou pela manutenção sem publicar (teto, intervalo mínimo, falta de pauta): antes disso, a troca forçada só acontecia nos dias em que saía matéria, e a meta ia a zero em silêncio nos outros.
- **Rodada sem publicação não deixa foto no disco.** `turno.js` tira o retrato de `images/posts` e `images/covers` no começo e apaga o que nasceu durante a rodada em toda saída sem publicação — é o `garantirFoto()` dele que baixa o jpg, minutos antes de o `publish.js` existir como processo, então o retrato do publish não pegava nada. `publish.js` mantém o dele (mais o gancho de `process.on("exit")`, para exceção sem catch) porque alguém roda o publish à mão. `turno.js` tem o mesmo gancho: um throw sem catch derruba a rodada antes do `finish()`, e no runner a vermelho o recuo geral encobre isso — na máquina do dono, não: por isso o `hwp-turno.sh` recusa árvore suja antes de começar. Ctrl+C e o `timeout 65m` (aqui) chegam por sinal. Onde o sinal pousa muda quem fecha a rodada, e isso foi medido em 15/11: um `node` bloqueado dentro de `execFileSync` **não** corre o listener de `SIGTERM` — o `timeout` mata o grupo inteiro, o filho morre, o `run()` devolve code 1 e é o caminho de erro normal que chama o `finish`. Fora de um filho bloqueado (o Ctrl+C entre etapas) é o listener de `SIGINT`/`SIGTERM` que chama o `finish`. As duas portas desfazem as fotos, escrevem o `TURNO.md` e saem vermelhas; o `timeout-minutes: 45` do workflow parado não conta porque o job é inerte no arquivo. O teto local é 65 min por aritmética, não por gosto: `turno.js` chama o redator até 3 vezes numa rodada (texto inicial + 2 reescritas do laço de correção), cada `write.js` tem parede de 14 min e os outros passos valem ~15 — 57 min de pior caminho. Os 8 min que sobram são da rede do runner, não folga: `fetch` + `merge --ff-only` antes e o push com até 3 tentativas depois, e é o `timeout 65m` que decide a corrida quando a rede não decide. O `TimeoutStartSec` do serviço fica em 78 min, ACIMA do script, para que quem mate a rodada seja sempre o `timeout` do runner: só ele faz o recuo, commita o diário e empurra. Se o systemd vencer, a árvore fica suja e o horário seguinte morre no portão da árvore — dois horários perdidos em vez de um. Terceira boca: a folga do vigia (90 min) tem de continuar acima das duas, senão a olhada canta "servida e empurrada" numa rodada que ainda está escrevendo.

## A nota (Camada 2.5): calculada, nunca digitada

`tools/score.js` dá 0–10 a cada matéria somando seis critérios, cinco deles medidos:

| critério | peso | o que mede |
|---|---|---|
| evidence | 2,5 | fontes únicas, domínio diverso, quantas são primárias e datadas |
| timeliness | 1,5 | idade da fonte mais recente |
| novelty | 2,0 | sobreposição de vocabulário com o catálogo (≥72% = quase-duplicata, −2,0 e bloqueio) |
| craft | 2,0 | o que `check-post.js` medeu em `metrics.json`: ritmo, léxico banido, humor, tamanho vs. brief |
| commercial | 1,0 | produto com preço, caixa de afiliado, protocolo de teste |
| judgment | 1,0 | o único ponto de opinião do modelo (`ranking.thesis_strength`, 0–2, com justificativa de até 25 palavras) |

Penalizações: `analysis_only` −0,5, quase-duplicata −2,0, sem imagem −0,5. O modelo **não pode declarar a nota** — se o draft trouxer `ranking.score`, o check reprova. Notas ficam em `pipeline/scores.json` (versionado), com origem `auto`, `baseline` ou `manual`. Nota manual só entra pelo painel com justificativa de 15+ caracteres, e o recálculo nunca a sobrescreve.

## Camada 3: o turno agendado (roda sem você)

O robô roda nesta máquina: `~/.config/systemd/user/hwp-turno.timer` chama `~/.local/bin/hwp-turno.sh`, que atualiza o `main` por fast-forward, roda `node tools/turno.js`, commita `turno:` e empurra. O `OnCalendar` é `*-*-* 02,06,10,14,18,22:23:00` no fuso do sistema = 1/5/9/13/17/21 UTC, os seis horários do `check_hours` em `pipeline/cadence.json` e o mesmo cron escrito em `.github/workflows/turno.yml` — o arquivo continua no repo como a agenda conferível (é dele que `tools/lib/schedule.js` lê o relógio), mas o job está **inerte por construção** (`if: false # hwp:nuvem-inerte`) e o workflow desabilitado na aba: quem publica é o timer. A sequência, na ordem em que `turno.js` a executa: portão de horário (`lib/round-lock.js` — o slot já servido encerra a rodada cedo, antes de coletar) → `ingest.js` (acumulando a fila do dia) → **`build.js --daily`** (gira só os blocos de `"rotacao": "dia"` — hoje o Today's Picks — sem tocar na capa nem no contador; vem antes da manutenção porque o doctor cobra o bloco de hoje no ar, e até 10/11 quem o produzia era o build do fim da rodada: na virada do dia UTC o portão nascia vermelho por construção e a rodada nunca chegava a girar o bloco) → `doctor.js --offline` (para tudo se houver erro, e a rodada fecha vermelha) → teto diário **e** distância mínima da última publicação em `pipeline/cadence.json` (os dois **antes** de escolher pauta) → portão do redator (`lib/providers.js`: `armados() === 0` fecha a rodada **vermelha antes** do `pick-lead`, senão as seis rodadas do dia queimam seis pautas em `em_andamento` para descobrir que ninguém escreve — é a chamada do MESMO módulo do pré-voice do runner, não uma cópia) → `pick-lead.js` → `new-post.js` → escreve o `draft.json` seguindo `prompt.md` (o texto é do `write.js` na fila de provedores, e o primeiro da fila é o agente do app via `qodercli`, com as APIs HTTP atrás como reserva) → foto real → `make-cover.js` → `check-post.js` (máx. 3 correções) → `score.js` (para se for duplicata) → `publish.js`. Rodada que passa pela manutenção e não publica ainda chama o `build.js` completo para girar a capa. `tools/` nunca faz push, nunca faz deploy, nunca toca na identidade visual. O push é do runner — `hwp-turno.sh` aqui, a etapa final do workflow no Actions — e só acontece em `main`, nunca com `--force`. Prova do destravamento: `node .audit/teste-trava-picks.js`.

Publicar mais que isso em domínio recém-reativado é o perfil exato que os buscadores tratam como fábrica de conteúdo. O teto é 5 com 6 horários porque uma rodada entrega no máximo uma peça, e o sexto horário é a folga da rodada que morre no redator. A média real medida nos últimos 7 dias ainda está em ~1 peça/dia e é isso que o aviso `cadence-entrega` mostra sem fechar a rodada — mas parte do que parecia cautela editorial era mecânica: até 14/11 a fila do dia era reescrita a cada coleta e esvaziava antes do teto (13-19 pautas nos dias em que a última coleta foi a primeira, exatamente 1 nos dias de 4 rodadas). Com a fila acumulativa, os 5/dia passam a ser julgados pelo que são. Para furar o teto uma vez: `node tools/publish.js <slug> --force-cadence`. Antes disto, duas de três publicações de um mesmo dia tinham entrado furadas e nada no repositório dizia isso depois. Prova: `node .audit/teste-furo-cadencia.js`.

O `doctor.js` fecha **vermelho** se `max_publishes_per_day` passar desse número, se o `cron_expression` do JSON divergir do cron do workflow, e avisa se `checks_per_day` ou `check_hours` não baterem com o cron no fuso declarado. Foi essa conta que mostrou o primeiro buraco: com os horários antigos (07/10/14/17/21 UTC, dos quais 07/10/17 **nunca** dispararam no Actions) a agenda permitia 4 publicações contra uma meta declarada de 5 — verde dia após dia sem publicar nada.

Se o `pipeline/memory.json` estiver ilegível, o gap cai no histórico dos commits `publish:` — a trava não abre junto com o teto.

A trava de rascunho que o `pick-lead.js` usa para não reeleger a pauta de um `em_andamento` já vencido **vale enquanto vale a pena** (15/11): `tentadasComSlug` só bloqueia um slug enquanto alguma tentativa dele está dentro da `lead_retry_hours` — com um `em_andamento` vencido ainda gravado, a trava era eterna e a escolha passava a ser por exclusão, não por frescor. Quem é liberado sai no stderr (`pick-lead: N rascunho(s) de tentativa já vencida liberado(s) da trava…`). Prova: `node .audit/teste-trava-rascunho.js` (17 conferências).
- **Dois relógios no mesmo minuto é vermelho antes de começar.** O cron local e o do arquivo coincidem de propósito, então se o workflow for reabilitado na aba Actions as duas mãos escrevem em `pipeline/memory.json` — a mesma pauta marcada `em_andamento` duas vezes, duas rodadas queimando a mesma fonte. ### Rodar a bateria de provas sem pisar na rodada

As provas de `.audit/` não são leitura: `muta-slot-stale`, `teste-trava-arquivo`, `teste-trava-picks`, `teste-capa-rodada` e companhia escrevem dentro de `tools/` e de `pipeline/state/` do **próprio repo** e devolvem o arquivo no fim. Isso é seguro até o momento em que o `tools/` mutilado é exatamente o que a rodada do cron executa — e até o momento em que um Ctrl+C no meio da prova deixa o defeito no disco, porque o `finally` morre junto com o processo. Quem empurra é o runner com `git add -A`: uma prova interrompida commita um `build.js` quebrado.

Por isso a bateria entra por um portão, não por um `for`shell:

```bash
node .audit/roda-provas.js                    # a bateria inteira
node .audit/roda-provas.js teste-trava-picks  # só o que o nome casa
node .audit/roda-provas.js --pula provedor    # exclui por trecho
node .audit/roda-provas.js --forcar           # ignora SÓ a janela de horário
```

Quatro coisas ele garante, e cada uma existe por um motivo medido:

- **árvore limpa na entrada.** Com rastreado sujo, nada roda (exit 1) — devolver ao estado anterior seria apagar trabalho seu. O que já era **não rastreado** antes da bateria é lembrado e nunca apagado; foi assim que o próprio `roda-provas.js`, recém-criado, sobreviveu à primeira execução.
- **fora da janela da rodada.** Segura o `flock` do cinto (`~/.local/state/hwp/turno.lock`) e calcula, no fuso do `cadence.json`, a distância ao próximo horário; menos de 20 min (`HWP_PROVAS_FOLGA`) barra. É o tempo que a bateria precisa de árvore estável.
- **restauração por bytes, não por `git checkout`.** Na entrada, com o rastreado provado limpo, os bytes do disco SÃO o estado da entrada, e ele espelha `tools/`, `pipeline/`, `js/`, `voice/`, `css/` e a raiz num diretório temporário. O `checkout` devolveria o blob — com `core.autocrlf=input` nesta máquina, os `tools/*.js` vivem CRLF no disco e LF no objeto, então o checkout verdeja o git e muda os bytes; `teste-trava-arquivo` compara hash de arquivo, e é ele que acusaria. Fora do espelho a volta é pelo HEAD e a linha diz qual das duas bocas foi usada.
- **o placar fecha conferindo a árvore.** `exit`, SIGINT, SIGTERM e SIGHUP passam pela mesma restauração, e no fim cada caminho espelhado é comparado byte a byte contra a entrada; resíduo ou divergência é vermelho mesmo com todas as provas verdes.

Roda do Windows herdada que ficou de fora, declarada: `verify.js` e os `cdp*.js` chamam Chrome em `C:/Program Files/…` contra um servidor em `:8080`. Não são portões do pipeline e uma boca vermelha permanente no placar é o ruído que esconde a vermelha de verdade. (15/11: 22 provas, 474 conferências, zero resíduo.)

### Histórico

O projeto é um repositório Git (branch `main`, remoto `github.com/yuryfigueiredo/Site-wordhomepress`). Cada publicação vira um commit; o baseline `82c6db3` é o site auditado. `pipeline/drafts/`, `pipeline/leads/`, `pipeline/state/` (menos `cover-state.json` e `hero-fallback.html`, que precisam sobreviver ao runner limpo) e `tools/reports/` estão no `.gitignore` porque rascunho não publicado em repositório público é rascunho publicado. Push em `main` agora é deploy: a Vercel publica a cada push.

## O que continua dependendo de gente

- **Domínio.** O site está no ar em `site-homeworldpress.vercel.app`, mas os canonicals de todas as páginas apontam para `homeworldpress.com` — e esse domínio ainda responde com a página de estacionamento do GoDaddy. Enquanto os nameservers não forem trocados no DomainControl, o Google vê um canonical que não é o site. Passo a passo em [PUBLISHING.md](PUBLISHING.md).
- **Conta Amazon Associates.** Sem a sua Store ID real, os 184 links com a tag `homeworldpres-20` não rendem nada. Depois de aprovado, a troca é `node tools/set-affiliate-tag.js <sua-tag>` (acima).
- **"Nós testamos."** Só sai da sua mão. Sem aparelho na mão, o texto é comparação de especificações e precisa se chamar isso.
- **Fotos de produto.** As imagens do review de e-readers são Unsplash, e algumas não batem com o produto (tem luminária ilustrando um Kindle Scribe).
- **Direito de imagem de capas.** As capas históricas da editora vêm do arquivo do James Gauthier; antes de publicar, confirme a permissão por escrito.
- **Medição de tráfego.** Hoje não há nenhuma: escolher entre Google Search Console (o dado que decide a estratégia de afiliado) e um script de analytics é decisão sua.
- **Nota manual no painel.** Opcional. Serve para corrigir o robô quando ele erra de julgamento, não para substituí-lo.
